# ConfPlanner

**ConfPlanner** — персональный self-hosted Telegram-бот с AI-агентом для поиска, исследования и отслеживания научных конференций. Он использует сохранённые научные интересы, источники пользователя и веб-поиск, проверяет страницы мероприятий, ведёт кандидатов и отслеживает дедлайны.

Бот рассчитан на одного владельца. Управление доступно через обычные сообщения в Telegram и постоянное меню. Все изменения пользовательских данных, требующие подтверждения, выполняются только после соответствующего действия владельца.

## Возможности

- Диалог с LLM в Telegram, поддержка Ollama Cloud и локального OpenAI-совместимого API; переключение через `/model`.
- Поиск конференций через **SearXNG** и **независимый прямой обход** включённых источников из меню «Источники» (`PAGE` и `DOMAIN`). Если поисковые движки ограничивают запросы, обход источников может продолжаться.
- Многоуровневый обход каталогов и раскрытие ссылок на конкретные мероприятия.
- Глубокое исследование HTML-страниц: приоритет для научной программы, тем, секций, докладов, постеров и тезисов, если они опубликованы на сайте.
- Семантическая оценка релевантности по извлечённому содержимому и научным темам пользователя с помощью LLM. Название конференции и совпадение ключевых слов сами по себе не являются доказательством релевантности.
- Проверка года, дат, места, организаторов, официальных URL и дедлайнов; хранение источников и истории изменений.
- **Playwright + Chromium** для страниц, содержимое которых появляется после выполнения JavaScript.
- **Постоянная очередь URL в SQLite**, восстановление незавершённого обхода после перезапуска контейнера.
- **Только веб-страницы**: PDF, DOC/DOCX, таблицы, презентации, архивы и другие файловые URL исключаются из обхода и проверки.
- Отчёт об исследовании и карточка статуса в Telegram с согласованными счётчиками из SQLite. Отчёт «Подробности» обновляется в существующем сообщении.
- Карточки кандидатов, действия «Отслеживать», «Пропустить», «Отклонить», подтверждение изменений.
- Плановый мониторинг конференций, напоминания о дедлайнах, долговременная память и граф связей на SQLite.

> **Важно:** сохранённая ссылка-кандидат, успешно открытый каталог и успешно исследованная страница — разные результаты. Ни один из них сам по себе не означает, что найдена подтверждённая релевантная конференция нужного года.

## Архитектура

Docker Compose поднимает **три сервиса**:

| Сервис | Назначение |
|---|---|
| `confplanner` | Telegram-бот (aiogram), планировщик APScheduler, агент, MCP, исследование сайтов, доступ к SQLite |
| `searxng` | Внутренний метапоиск; отдельные внешние поисковые движки могут отвечать CAPTCHA/403/429 |
| `browser-worker` | Изолированный Playwright/Chromium для резервного JavaScript-рендеринга |

Основные компоненты приложения: `WorkflowEngine`, исследование конференций, `PageFetcher`, модельный шлюз, SQLite/SQLAlchemy и миграции Alembic. Браузерный сервис не имеет опубликованного порта; бот обращается к нему по внутренней сети Compose. MCP также предназначен для внутреннего использования.

### Как получается содержимое сайта

1. Выполняется обычный HTTP-запрос и очистка HTML.
2. Если ответ похож на пустую JavaScript-оболочку, страница повторно открывается через Chromium.
3. Из отрендеренного HTML извлекаются текст и ссылки.
4. Данные используются для классификации страниц и исследования конференции.

Chromium **не** запускается для каждого URL, не обходит CAPTCHA и не гарантирует получение содержимого сайтов с авторизацией, интерактивными фильтрами, бесконечной прокруткой или жёсткими антибот-ограничениями. Внешние сайты рассматриваются как недоверенные данные.

## Поиск: актуальный процесс

Запрос «Найди релевантные моим темам конференции на 2027 год» создаёт задание `discovery_jobs` и запускает исследование в существующем `WorkflowEngine`.

1. **Получение контекста.** Учитываются запрос, год, научные темы и сохранённые правила владельца.
2. **Обнаружение.** Используются все включённые пользовательские источники и SearXNG; источники обходятся напрямую, даже если SearXNG недоступен.
3. **Раскрытие каталогов.** Находятся вложенные HTML-страницы и ссылки на отдельные мероприятия. Ссылки нормализуются и дедуплицируются.
4. **Предварительная классификация.** Каталоги направляются в обход, возможные страницы конференций — в проверку; очевидно посторонние страницы, неподходящие годы и документы исключаются либо понижаются в приоритете.
5. **Приоритизация.** Выше ставятся страницы реальных мероприятий, соответствующие запрошенному году и научной тематике, и известные официальные научные источники. Общие каталоги не должны расходовать бюджет проверки как отдельные конференции.
6. **Углублённая проверка.** Открываются страницы конференций и связанные HTML-страницы с программой, тематикой, секциями, докладами, постерами и тезисами. Сведения передаются механизму извлечения и LLM-оценки релевантности.
7. **Сохранение результатов.** Отдельно фиксируются проверенные страницы, неподходящие/истёкшие мероприятия, технические ошибки и ещё не исследованные кандидаты.
8. **Продолжение.** Если за один проход не обработана вся очередь, незавершённые URL сохраняются для дальнейшего выполнения.

### Бюджеты исследования

Нет фиксированного ограничения **на общее число сохраняемых кандидатов** и прежнего лимита в 12 проверок. Однако один проход ограничен ресурсами, чтобы обход не стал бесконечным.

| Параметр | Текущее значение по умолчанию |
|---|---|
| Глубина прямого обхода каталогов | `4` |
| Открываемых страниц каталогов за один проход | `200` |
| Время углублённого исследования за один проход | `1200` секунд |
| Связанных страниц-доказательств на мероприятие | До `18` |
| Повторных попыток URL-задачи | До `3` |

Ограничения одного прохода **не означают удаление оставшихся кандидатов**: очередь сохраняется в SQLite. При этом полнота обнаружения зависит от доступности сайтов, качества извлечения, времени выполнения и модели — «глубокий поиск» не означает гарантированно полный каталог всех существующих мероприятий.

### Оценка релевантности

Наиболее содержательные признаки — **темы и секции научной программы, названия и содержание докладов, постеры, тезисы, цели конференции**. Проверяются связь с интересами владельца, соответствие указанному году, организатор и происхождение данных. Оценка должна опираться на извлечённые сведения со страниц, а не на один URL или заголовок.

Если программа ещё не опубликована или недоступна, релевантность нельзя считать достоверно подтверждённой только по общему описанию. PDF-версии программ и тезисов **сознательно игнорируются**: бот исследует исключительно веб-страницы.

## Возобновляемая очередь

В миграции `20261030_0021_discovery_url_tasks.py` добавлена таблица `discovery_url_tasks`.

- `CATALOG` — задача обхода каталога; `INSPECT` — проверка страницы кандидата.
- `PENDING` — ожидает; `RUNNING` — выполняется; `DONE` — завершена; `FAILED` — не удалась; `SKIPPED` — пропущена (например, документ).
- URL нормализуются; уникальная комбинация `(job_id, normalized_url, task_type)` предотвращает дубли задач в одном задании.
- В SQLite фиксируются попытки, результаты, отметки времени и `lease_until` для захваченных задач.
- После перезапуска истёкшие `RUNNING` могут возвращаться в обработку; `DONE` не должны повторно исследоваться без необходимости.
- При повторном обнаружении одной страницы найденные ранее кандидаты не должны дублироваться.

**Ограничение:** восстановление работает на уровне URL-задачи, а не с середины HTTP-загрузки. Сетевая операция, которая всё ещё зависла внутри работающего процесса, может задержать очередь; одно лишь истечение `lease_until` не прерывает такой запрос. Очередь рассчитана на один экземпляр обработчика ConfPlanner, а не на параллельные реплики.

### Игнорирование файлов

В обход и `INSPECT` не допускаются ссылки на PDF, DOC/DOCX, XLS/XLSX, PPT/PPTX, CSV, архивы, изображения, мультимедиа и другие известные файловые форматы. Ранее поставленные в очередь файловые URL получают `SKIPPED` с причиной `NON_HTML_DOCUMENT`; исходные записи остаются в базе. Возможные исключения, например загрузка файла по URL без расширения, зависят от проверок HTTP-ответа.

## Прогресс и отчёт Telegram

При запуске поиска бот создаёт карточку задания с кнопками **«Статус», «Подробности», «Отменить»**.

- Статус и подробности рассчитывают показатели по одним записям `DiscoverySearchAudit` и `DiscoveryURLTask` в SQLite.
- Отдельно учитываются открытые страницы источников, успешно проверенные страницы кандидатов, раскрытые каталоги, отклонения по содержимому, технические ошибки, ожидающие/выполняемые задачи и пропущенные файлы.
- Первое нажатие «Подробности» открывает отдельное сообщение с отчётом; дальнейшие нажатия **редактируют его**, а не создают новые сообщения. При активном поиске отчёт может обновляться автоматически.
- В кратком отчёте может отображаться только часть последних записей журнала; суммарные счётчики относятся ко всему заданию.
- «Отменить» запрашивает кооперативную остановку обработки.

`RESEARCHED` означает, что страницу удалось исследовать, **не** то, что она подтверждена как релевантная конференция 2027 года. `ModelGatewayError` и `FetchError` означают технические проблемы, а неподходящее или прошедшее мероприятие следует отличать от технического сбоя.

## Требования

- Docker Engine и Docker Compose v2 на Linux-хосте/VM.
- Сеть для Telegram, внешних сайтов, поисковых систем и выбранного LLM API.
- Telegram-токен бота и числовой ID владельца.
- Ключ Ollama Cloud **или** доступ к собственному OpenAI-совместимому API.
- Достаточно оперативной памяти для Chromium (для `browser-worker` в Compose установлен лимит `1500m`).

Для запуска приложения без Docker нужен Python 3.12+ и `uv`; при таком способе браузерный сервис потребует отдельного развёртывания.

## Быстрый запуск

```bash
git clone https://github.com/annaromanovskaya/conference-planner.git ConfPlanner
cd ConfPlanner
cp .env.example .env
```

Заполните `.env` и выполните:

```bash
docker compose up -d --build
docker compose ps
docker compose logs --tail=100 -f confplanner
```

Откройте Telegram-бота, отправьте `/start`, затем `/model` и выберите доступную модель. Для действий с инструментами модель должна поддерживать OpenAI-совместимые tool calls.

### Telegram

```dotenv
TELEGRAM_BOT_TOKEN=YOUR_TELEGRAM_BOT_TOKEN
OWNER_TELEGRAM_ID=YOUR_TELEGRAM_ID
```

Токен создаётся в `@BotFather`. Не добавляйте `.env` в Git.

### Ollama Cloud

```dotenv
OLLAMA_CLOUD_BASE_URL=https://ollama.com
OLLAMA_CLOUD_API_KEY=YOUR_OLLAMA_CLOUD_API_KEY
OLLAMA_CLOUD_FREE_MODELS=gemma4:31b,gpt-oss:120b,gpt-oss:20b,nemotron-3-nano:30b,nemotron-3-super,nemotron-3-ultra
```

В `/model` доступны модели из пересечения разрешённого списка и ответа Ollama. Учёт токенов в боте — локальная статистика, а не точный остаток облачного лимита. Платные списания при разрешении их в аккаунте контролируются настройками самого провайдера.

### Локальный OpenAI-совместимый API

```dotenv
LLM_LOCAL_BASE_URL=http://llm-server.local:1337/v1
LLM_LOCAL_API_KEY=YOUR_LLM_LOCAL_API_KEY
```

Необходимы `GET /v1/models`, `POST /v1/chat/completions`, tool calls и, для структурированного извлечения, поддержка `response_format` с JSON Schema. Базовый URL обычно заканчивается на `/v1`, без `/models` или `/chat/completions`. Адрес должен быть доступен **из контейнера**, а не только с хоста. Внутри Docker `127.0.0.1` указывает на сам контейнер.

Для ролей агента можно назначить разные модели:

```dotenv
AGENT_SUPERVISOR_MODEL=
AGENT_RESEARCH_MODEL=
AGENT_VERIFIER_MODEL=
AGENT_FALLBACK_MODEL=
```

Пустое значение означает использование модели, выбранной через `/model`.

### Основные переменные `.env`

```dotenv
AGENT_MAX_STEPS=6
AGENT_MAX_TOOL_CALLS_PER_STEP=3
AGENT_TIMEOUT_SECONDS=300
TRACKED_CHECK_TIMEOUT_SECONDS=300
AGENT_MAX_CONTEXT_CHARS=24000
AGENT_MAX_TOOL_RESULT_CHARS=12000
AGENT_WORKFLOWS_ENABLED=true

DATABASE_URL=sqlite+aiosqlite:////data/conference_planner.db
SEARXNG_URL=http://searxng:8080
READER_FALLBACK_URL=https://r.jina.ai
REQUEST_TIMEOUT_SECONDS=20
MAX_PAGE_BYTES=2000000
MAX_PAGE_TEXT_CHARS=50000

MCP_HOST=127.0.0.1
MCP_PORT=8765

DISCOVERY_INTERVAL_HOURS=168
MONITORING_INTERVAL_HOURS=72
REMINDER_HOUR=9
REMINDER_DAYS=30,14,7,3,1,0
MIN_RELEVANCE_SCORE=0.5
APP_TIMEZONE=Europe/Moscow
LOG_LEVEL=INFO
```

Дополнительные переменные глубокого поиска читаются непосредственно в `app.py`:

```dotenv
DISCOVERY_CRAWL_DEPTH=4
DISCOVERY_CRAWL_MAX_PAGES=200
DISCOVERY_INSPECTION_SECONDS=1200
```

**Внимание:** эти три переменные сейчас считываются через `os.getenv()`. Чтобы переопределить их в Docker, нужно передать их в окружение сервиса `confplanner` через `compose.yaml` (например, секцию `environment:`), а не просто вписать в `.env`, если Compose их не пробрасывает. В `compose.yaml` уже настроен внутренний `BROWSER_RENDER_URL=http://browser-worker:8765/render`.

`REQUEST_TIMEOUT_SECONDS` — общий HTTP-тайм-аут клиента; его увеличение может влиять и на ожидание LLM. Это не специализированный тайм-аут только для модели.

## Кандидаты, память и подтверждения

Кандидаты отображаются по одному с доступными сведениями о мероприятии, источнике, годе, сроках, тематике и проверке. Возможны действия «Отслеживать», «Пропустить», «Отклонить», а также просмотр подробностей. Пропущенные и отклонённые кандидаты обрабатываются отдельно от новых.

Долговременная память хранит подтверждённые научные интересы, регионы, предпочтения, ограничения и заметки. `/new` не удаляет память. Изменения данных инициируются через подтверждаемые действия; повторное применение уже исполненного или устаревшего действия блокируется.

## Мониторинг и напоминания

Плановый агентский цикл запускается каждые `DISCOVERY_INTERVAL_HOURS` часов (по умолчанию 168). Отдельный интервал мониторинга известных страниц — `MONITORING_INTERVAL_HOURS` (72 часа по умолчанию). Плановый цикл и интерактивный глубокий поиск могут иметь разные бюджеты работы.

Сохраняются точные и ориентировочные сроки: начало регистрации, ранняя/окончательная регистрация, подача тезисов, уведомление о принятии, оплата и другие события. Источник даты и история изменений фиксируются; отсутствие точного дня не должно приводить к выдумыванию числа.

Напоминания отправляются по правилам `REMINDER_DAYS`; по умолчанию за 30, 14, 7, 3, 1 и 0 дней до дедлайна. `/test_reminder` создаёт временную проверку доставки; `/cancel_test_reminder` удаляет её.

## Эксплуатация и обновление

```bash
# Пересоздать приложение после изменения исходников или .env
docker compose up -d --build --force-recreate confplanner

# После изменения браузерного сервиса или Compose
docker compose up -d --build --force-recreate browser-worker confplanner

# Состояние сервисов и логи
docker compose ps
docker compose logs --tail=100 confplanner browser-worker searxng
```

Alembic автоматически применяет миграции при старте приложения. Перед обновлением, затрагивающим схему SQLite, сделайте резервную копию.

### Резервная копия SQLite

Онлайн-копирование через SQLite Backup API не требует остановки бота:

```bash
docker exec confplanner python -c '
import sqlite3
src = sqlite3.connect("/data/conference_planner.db")
dst = sqlite3.connect("/data/conference_planner.backup.db")
src.backup(dst)
dst.close()
src.close()
'
```

Копия создаётся **в том же Docker volume**, поэтому для защиты от отказа диска её затем необходимо перенести на независимое хранилище. Не удаляйте `.db-wal` и `.db-shm` при работающем приложении. SQLite использует WAL и тайм-аут ожидания блокировок.

### Проверка очереди URL

```bash
docker exec -i confplanner python - <<'PY'
import sqlite3
c = sqlite3.connect('/data/conference_planner.db')
for row in c.execute('''
    SELECT job_id, task_type, status, COUNT(*)
    FROM discovery_url_tasks
    GROUP BY job_id, task_type, status
    ORDER BY job_id DESC, task_type, status
'''):
    print(row)
PY
```

`CATALOG / DONE` означает, что каталог обработан; `INSPECT / PENDING` — что кандидат ожидает проверки; `INSPECT / RUNNING` — что выполняется проверка. Если статус `RUNNING` долго не меняется, проверьте время `updated_at`, `lease_until` и логи приложения. Сам факт наличия очереди ещё не гарантирует, что зависший сетевой вызов будет принудительно остановлен.

### Проверка SearXNG

```bash
docker exec -i confplanner python - <<'PY'
import json, urllib.parse, urllib.request
params = urllib.parse.urlencode({'q': 'astronomy conference 2027', 'format': 'json'})
url = 'http://searxng:8080/search?' + params
with urllib.request.urlopen(url, timeout=20) as r:
    result = json.load(r)
print('Results:', len(result.get('results', [])))
print('Errors:', result.get('unresponsive_engines'))
PY
```

Google и Google CSE могут отвечать `access denied` или `too many requests`. Это ограничения внешних систем, не доказательство полной недоступности SearXNG; доступны альтернативные поисковые движки и обход сохранённых источников. SearXNG не обходит CAPTCHA.

### Проверка LLM

Сначала проверьте доступность `GET /v1/models` из контейнера. Успешный ответ `/models` не гарантирует работу генерации: при проблемах дополнительно проверяйте `POST /v1/chat/completions` и структурированный `response_format`. Ошибка `ModelGatewayError` может обозначать тайм-аут, HTTP-ошибку или некорректный ответ. Не выводите токены и полные запросы в публичные логи.

### Частые проблемы

| Симптом | На что обратить внимание |
|---|---|
| `TelegramConflictError` | Один Telegram-токен одновременно опрашивают два процесса |
| SearXNG вернул мало полезных страниц | `unresponsive_engines`, CAPTCHA/429, качество поисковых запросов |
| `ModelGatewayError` | Доступность API, фактическая модель, тайм-ауты, поддерживаемые параметры |
| Долго нет изменений в очереди | `RUNNING`, `lease_until`, тайм-аут обработки URL, состояние воркера |
| JavaScript-сайт пуст | Логи `browser-worker`, наличие данных в DOM, антибот/интерактивная навигация |
| Не найдены сроки | Дата отсутствует в HTML, находится только в документе или не подтверждена источником |

## Безопасность и ограничения

- `.env` и ключи не должны попадать в Git или сообщения Telegram.
- Внешние страницы недоверенны; инструкции на них не имеют приоритета над правилами приложения.
- Проверяются публичные URL и ограничения доступа к внутренним/служебным сетевым адресам. Для Chromium желательна дополнительная сетевая изоляция на хосте; проверка IP внутри приложения не заменяет firewall.
- MCP и SearXNG не публикуются на внешнем интерфейсе Compose.
- Работа браузера ограничена ресурсами, JavaScript-загрузкой и доступностью сайтов.
- **PDF, Word, презентации, таблицы и прочие документы намеренно не исследуются.** Это также означает, что конференции, публикующие научную программу только в PDF, могут получить неполную оценку.
- Программа и темы конференции могут отсутствовать на сайте на момент поиска. Система не должна заполнять отсутствующие данные догадками.
- Некоторые сайты запрещают автоматическую загрузку или требуют ручную CAPTCHA; такие ограничения не обходятся.
- SQLite-очередь предназначена прежде всего для одного работающего экземпляра приложения.

## Устойчивость длительного исследования (30 октября 2026)

Каждый URL исследуется как отдельная задача в `discovery_url_tasks`. Для HTML-проверки задан
тайм-аут `DISCOVERY_INSPECT_TIMEOUT_SECONDS` (по умолчанию 180 секунд), для загрузки
каталогов — `DISCOVERY_CATALOG_TIMEOUT_SECONDS` (60 секунд). Ошибки повторяются максимум
три раза; повторы отложены на 30 и 90 секунд, новые URL имеют приоритет.

После перезапуска Docker незавершённые URL возвращаются в очередь и сохраняют количество
попыток. Продолжение задания не запускает заново завершённый SearXNG-поиск, а продолжает
сохранённые URL. Документы PDF/DOC/DOCX и прочие файлы не исследуются.

Миграция `20261030_0022_url_retry.py` добавляет дату следующей попытки. Она выполняется
автоматически при запуске. Перед обновлением сделайте резервную копию базы SQLite.

```bash
docker exec confplanner python -c 'import sqlite3; c=sqlite3.connect("/data/conference_planner.db"); print(*c.execute("SELECT job_id,task_type,status,count(*) FROM discovery_url_tasks GROUP BY 1,2,3 ORDER BY 1,2,3"), sep="\n")'
```
